# تطبيق الأرشفة Standard

نظام أرشفة مكتبي عام قابل للتثبيت والتخصيص لأي قسم، مبني باستخدام Flutter لنظام Windows، مع PHP API وقاعدة بيانات MySQL مستقلة.

## الفروع

- `main`: النسخة الأولى الخاصة بالقسم الإداري / وحدة العقوبات.
- `standard-version`: النسخة العامة Standard القابلة للتجهيز لأي قسم.

## وظائف التطبيق

- تسجيل دخول آمن لموظف الأرشفة.
- حفظ الملفات الرئيسية.
- إضافة الكتب التابعة وربطها بالملف الرئيسي.
- البحث عن الملفات والكتب التابعة.
- تعديل بيانات الملفات.
- متابعة حالة كل ملف.
- إضافة التنبيهات وإنهاؤها.
- السحب من جهاز الأرشفة بواسطة TWAIN.
- سحب صفحة واحدة أو عدة صفحات.
- تحويل الصور المسحوبة إلى PDF.
- حذف الصور المؤقتة فقط بعد نجاح إنشاء PDF.
- فتح ملفات PDF وطباعتها.
- تسجيل العمليات المهمة داخل سجل التدقيق.

## أوضاع السحب

### مستند واحد متعدد الصفحات

توضع جميع صفحات الكتاب في جهاز الأرشفة، ثم يحفظها التطبيق داخل ملف PDF واحد.

اسم الوضع داخل النظام: `single_document`

### كل ورقة مستند مستقل

يمكن وضع عدة أوراق منفصلة داخل جهاز الأرشفة، ثم يحفظ التطبيق كل ورقة باعتبارها مستندًا مستقلًا وملف PDF منفصلًا.

اسم الوضع داخل النظام: `separate_pages`

## قاعدة البيانات

اسم قاعدة بيانات نسخة Standard:

`document_archive_standard_db`

قاعدة بيانات Standard مستقلة تمامًا عن قاعدة بيانات النسخة الأولى، ولا تحتوي على بيانات أي قسم سابق.

## الـ API

مسار ملفات API داخل XAMPP:

`C:\xampp\htdocs\document_api_standard`

عنوان API المحلي:

`http://127.0.0.1/document_api_standard`

يجب تشغيل Apache وMySQL من XAMPP قبل تشغيل التطبيق.

## مسار الأرشيف

مسار حفظ المستندات المقترح:

`D:\DocumentArchive`

يجب إنشاء المجلد ومنح التطبيق صلاحية القراءة والكتابة داخله.

يمكن تغيير المسار عند تجهيز التطبيق لقسم جديد.

## جهاز الأرشفة

التطبيق مصمم للعمل على Windows مع أجهزة الأرشفة التي تدعم TWAIN، ومنها أجهزة Canon.

متطلبات جهاز الأرشفة:

- تثبيت تعريف TWAIN.
- توصيل الجهاز وتشغيله.
- تثبيت تعريف وبرنامج Canon المناسب.
- عدم تنفيذ عمليتي سحب في الوقت نفسه.

الصور الناتجة عن جهاز الأرشفة تكون مؤقتة، ولا تُحذف إلا بعد نجاح إنشاء ملف PDF والتحقق منه.

## إجراءات الأمان

تتضمن نسخة Standard الإجراءات التالية:

- عدم حفظ كلمة مرور الموظف داخل كود Flutter.
- تشفير كلمة مرور المستخدم داخل قاعدة البيانات باستخدام Password Hash.
- استخدام Token مؤقت بعد نجاح تسجيل الدخول.
- حفظ بصمة Token داخل قاعدة البيانات بدلًا من حفظه بصورته الأصلية.
- انتهاء جلسة تسجيل الدخول بعد مدة محددة.
- إمكانية إلغاء جلسات تسجيل الدخول.
- قفل الدخول مؤقتًا بعد تكرار المحاولات الخاطئة.
- استخدام مستخدم MySQL محدود الصلاحيات بدل حساب root.
- استخدام Prepared Statements في استعلامات قاعدة البيانات.
- التحقق من البيانات قبل حفظها.
- تحديد حجم طلبات API.
- منع الوصول إلى الملفات الواقعة خارج مجلد الأرشيف.
- التحقق من نوع وحجم وبصمة الملفات.
- عدم عرض تفاصيل أخطاء قاعدة البيانات للمستخدم.
- السماح بالاتصال المحلي فقط بالـAPI.
- تسجيل العمليات المهمة داخل Audit Logs.
- استخدام رقم إصدار لمنع تعارض التعديلات.
- عدم رفع كلمات المرور وبيانات الاتصال السرية إلى GitHub.

لا يمكن ضمان منع جميع الثغرات بصورة مطلقة، لذلك يجب تحديث البرامج والتعريفات وأخذ نسخ احتياطية دورية.

## تشغيل المشروع أثناء التطوير

نفّذ الأوامر التالية من داخل مجلد المشروع:

`flutter pub get`

`flutter analyze`

`flutter run -d windows`

## بناء نسخة Windows

بعد نجاح الاختبارات:

`flutter build windows --release`

توجد النسخة الناتجة عادةً داخل:

`build\windows\x64\runner\Release`

يجب نقل مجلد `Release` كاملًا عند تشغيل التطبيق على جهاز آخر.

## تجهيز التطبيق لقسم جديد

1. إنشاء قاعدة بيانات مستقلة.
2. إنشاء مستخدم MySQL محدود الصلاحيات.
3. إعداد ملفات API وربطها بقاعدة البيانات الجديدة.
4. إنشاء حساب موظف الأرشفة الأول.
5. حذف ملف إنشاء المستخدم الأول بعد استخدامه.
6. تحديد مجلد أرشيف مستقل.
7. تثبيت تعريف جهاز الأرشفة.
8. اختبار تسجيل الدخول والسحب والحفظ والبحث والطباعة.
9. إعداد النسخ الاحتياطي الدوري.

يجب عدم نسخ بيانات قسم سابق إلى القسم الجديد.
